# D1 free tier capacity, 2026-11-01

Question: how large can the game catalog and its MiMMa scores grow before the app outgrows the
Cloudflare free tier?

Answer: storage is not the limit. Score reads are. Each game page reads about 28 database rows for
every scored game, so the 5 million free daily reads cover about 17,000 game page views a day at
today's 10 games, about 180 at 1,000 scored games, and about 2 at 100,000. Similar games also
exceeds the 10 ms CPU limit per request somewhere past about 1,000 scored games. The catalog shelf
and slug lookups stay flat at any size.

All numbers were measured on branch `feat/backlog-next-steps` at `c2a0705`, in the local runtime.
They have not been checked against production.

## Free tier limits

Taken from Cloudflare's D1 pricing and limits pages and the Workers limits page on 2026-11-01.

| Limit                         | Workers Free plan |
| ----------------------------- | ----------------- |
| D1 rows read                  | 5,000,000 per day |
| D1 rows written               | 100,000 per day   |
| D1 database size              | 500 MB            |
| D1 storage per account        | 5 GB              |
| Worker CPU time               | 10 ms per request |
| Worker requests               | 100,000 per day   |
| D1 queries per Worker request | 50                |

D1 counts rows scanned, not rows returned. A query that returns one row but scans a 5,000-row table
costs 5,000 reads. Index entries count as extra rows written.

## Method

1. Copy the local D1 database after `check:local` applied migrations 0001 to 0007 (10 catalog
   games, snapshot v2).
2. Grow it to 1,000, then 10,000, then 100,000 catalog games. Every new game copies the text of the
   Counter-Strike 2 row (description, tags, URLs), so row sizes match real data. Every new game
   gets an authority game, a score version, and a verified Steam mapping. Scores are spread
   deterministically over 1 to 99 on each axis.
3. At each size, freeze a new snapshot that holds every scored game, the way a real release would.
4. Call the real `handleRequest` from `src/worker/router.ts` (bundled with esbuild) with a D1
   binding from wrangler's `getPlatformProxy`. A wrapper records D1's own `rows_read` for every
   query. Each route is called twice and the second call is recorded.
5. Insert all data through the same binding, so D1 also reports `rows_written`.
6. Time the JavaScript work of similar games (parse tags, then `rankSimilarGames`) separately, on
   synthetic candidate lists with 8 tags each.

Every game is scored, which is the worst case for the score queries. With fewer scored games, the
score routes scale with the number of scored games, and search scales with the number of catalog
games.

`wrangler d1 execute --local` does not report `rows_read`, which is why the measurement goes
through `getPlatformProxy`.

## Results

### Rows read per request

| Request                            | 1,000 games | 10,000 games | 100,000 games |
| ---------------------------------- | ----------- | ------------ | ------------- |
| `/api/catalog`, either sort        | 52          | 52           | 52            |
| `/api/catalog?search=elden`        | 1,002       | 10,002       | 100,002       |
| `/api/games/elden-ring`            | 7,011       | 70,011       | 700,011       |
| `/api/games/elden-ring/similar`    | 21,008      | 210,008      | 2,100,008     |
| Game page visit (detail + similar) | 28,019      | 280,019      | 2,800,019     |

Every API request also reads 2 rows for the dataset version. The game page in the UI calls both
the detail and the similar endpoints, so one visit costs the sum. On today's unmodified database
(10 catalog games), the same requests read 12, 81, and 218 rows.

### Game page views per day on 5M reads

| Scored games | Reads per visit | Visits per day |
| ------------ | --------------- | -------------- |
| 10 (today)   | 299             | about 17,000   |
| 1,000        | 28,019          | about 180      |
| 10,000       | 280,019         | about 18       |
| 100,000      | 2,800,019       | about 2        |

### CPU for similar games

| Candidates | Parse tags and rank, per request |
| ---------- | -------------------------------- |
| 1,000      | 5.9 ms                           |
| 10,000     | 39.1 ms                          |
| 100,000    | 348.2 ms                         |

Measured on a desktop with Node 24. This excludes the cost of decoding D1 rows, which also counts
as Worker CPU. Workers hardware differs, so treat the 1,000-game threshold as approximate.

### Rows written

| What is added                        | Rows written         |
| ------------------------------------ | -------------------- |
| One catalog game                     | 8                    |
| One score (game, version, mapping)   | 16                   |
| One snapshot member                  | 3                    |
| New scored game, first snapshot      | 27                   |
| A snapshot of N scored games         | 3 × N                |
| Initial load of 100,000 scored games | about 2.7M (27 days) |

The free tier allows about 3,700 new scored games a day. A snapshot that holds more than about
33,000 games cannot be published within one day's write quota. Every snapshot copies every scored
game, so these costs repeat on every score release, not only on the first.

### Storage

At 100,000 scored games with three snapshots (111,000 member rows), the database was 189 MB. The
largest parts: `games` 49 MB, score versions 21.8 MB, mappings 18.6 MB, authority games 13.9 MB,
and snapshot members about 19 MB including their indexes.

That is about 1.7 KB per scored game, plus about 175 bytes per game for each full snapshot. The
500 MB limit would hold roughly 250,000 scored games with a few snapshots.

## Why the score routes scale with the catalog

`latestMappingCte` in `src/worker/repositories/authoritative-scores.ts:74-113` runs on every
request. It finds the latest mapping for every game, keeps the verified ones, and then runs two
`GROUP BY` checks over all of them to drop conflicting mappings. The game detail query needs one
game but pays for the whole table: 7 rows read per mapping.

`findScoredSimilarityCandidates` runs the same checks and then returns every scored game to the
Worker. The Worker parses each game's tags and ranks all of them in JavaScript to keep the top 5.
That is 14 more reads per scored game, plus CPU that grows with the catalog.

Search uses `title LIKE '%x%'`. A leading wildcard cannot use an index, so every search scans the
whole `games` table.

## Options

Scores change only when a snapshot is released. The per-request work can move to release time.

1. **Current score per game.** When a snapshot is frozen, write one row per catalog game with its
   current score. The conflict checks then run once, in the migration and the production verifier.
   The game page reads 1 row instead of 7 per scored game.
2. **Similar games per game.** At the same time, store the top 5 similar games for each game.
   Similar games then reads 5 rows and does almost no CPU work. The cost moves to release: at least
   5 rows written per scored game, plus index entries, which adds to the snapshot write budget
   above.
3. **Search.** Use FTS5 (SQLite's full-text index, which D1 supports), or match title prefixes
   against the existing title index.
4. **Snapshot size.** If snapshots grow past the daily write quota, either spread a release over
   several days or store only the games whose scores changed, with readers falling back to the
   previous snapshot. The second option changes the append-only design and needs its own decision.

Options 1 and 2 keep the append-only tables as the source of truth. The new tables are derived from
them and can be rebuilt.

## Limits of this measurement

- The local runtime counts reads with the same SQLite engine that D1 uses, but the numbers were not
  compared against a production database.
- The synthetic games share one row's text. Real descriptions and tag lists vary in length, which
  changes storage, not row counts.
- Edge caching is not modeled. The API sets `Cache-Control: public, max-age=60`, but a Worker
  response does not go through Cloudflare's cache unless the Worker uses the Cache API, so every
  request reaches D1. Browsers may still reuse a response for 60 seconds.
- Sign-in, sessions, and future community scores are not included. They add writes per user, not
  per game.
